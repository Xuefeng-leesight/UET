# UST License 与版本管理接口文档

> 文档版本：1.1.0
> 更新日期：2026-08-23
> 服务端实现：`backend/license_admin`  
> OpenAPI：`docs/接口/openapi.yaml`

## 1. 接入约定

### 1.1 地址与格式

- 开发地址：`http://127.0.0.1:8000`
- API 前缀：`/api/v1`
- 除安装包下载外，请求和响应均为 `application/json; charset=utf-8`。
- 时间统一返回 UTC ISO 8601，例如 `2026-08-22T08:00:00Z`。
- 资源 ID 为 UUID；版本号遵循语义版本。

生产地址由部署环境确定，客户端必须允许通过受控配置切换 API Origin，正式环境必须使用 HTTPS。

### 1.2 请求 ID

客户端建议每次请求发送唯一请求头：

```http
X-Request-ID: 0198d1de-4b94-7a90-8950-68a66e629a3a
```

服务端在响应头中回传同一值；值缺失或格式非法时服务端自动生成。报错时请连同请求 ID 一起提交，便于定位服务端日志。

### 1.3 认证

| 接口区域 | 认证 |
| --- | --- |
| `/api/v1/client/*`、健康检查 | 不使用账户认证；按 IP 限流，授权接口用 License key 校验 |
| `/api/v1/management/*` | Django Session 或 HTTP Basic；账户必须 `is_staff=true` |
| `/admin/*` | Django 后台登录 |

License key 相当于激活凭证，禁止写入普通日志或截图公开。管理 API 的 Basic Authentication 只允许在 HTTPS 下使用。

### 1.4 统一错误

```json
{
  "error": {
    "code": "DEVICE_LIMIT_REACHED",
    "message": "已达到设备激活上限。",
    "request_id": "0198d1de-4b94-7a90-8950-68a66e629a3a",
    "details": {
      "max_devices": 1,
      "active_devices": 1
    }
  }
}
```

客户端应以 `error.code` 分支处理，不要匹配中文 `message`。未知错误码按通用失败处理并保留请求 ID。

## 2. 推荐客户端时序

### 2.1 软件激活入口与职责边界

- `/admin/licensing/license/` 是运营后台的 License 管理页，只供有权限的后台人员使用，桌面客户端不得打开、嵌入或依赖该页面。
- `http://127.0.0.1:8000` 仅是本机开发地址。生产软件必须连接部署方提供的 HTTPS API Origin。
- 软件首次启动或本地不存在有效授权时，显示独立激活页，让用户输入形如 `UST-ABCD-EFGH-JKLM-NPQR` 的 License key。
- `machine_code`、`device_name` 和 `client_version` 由软件自动采集，终端用户不需要手工填写。
- 激活成功后，后台自动创建或更新 `LicenseDevice`。它表示安装并激活 UST 软件的电脑，不是 A8、Pro 等物理眼动设备。

建议激活页至少包含 License 输入框、“在线激活”和“导入离线授权”入口。设置页的 License 管理区域显示脱敏授权号、客户、授权模块、到期时间、当前电脑，并提供刷新、解绑操作。

第一版离线激活页提供“复制机器码”，不实现尚无服务端导入契约的离线申请文件。用户把机器码交给运营人员，运营人员调用管理端离线签发接口生成 `.lic`，用户再导入软件。导入 `.lic` 不代表自动可信，仍须执行第 6 节的全部本地验证。当前接口允许 `device_name`、`client_version` 为空，因此自动采集失败不阻断激活，但软件应尽量提供便于后台识别和排障的值。以后如需导出申请文件，须先定义版本化文件格式和管理端导入接口。

### 2.2 首次在线激活

```text
读取机器码
  → POST /client/activations
  → 获取签名 License 信封
  → 从客户端预置信任集合读取 key_id 对应公钥/指纹
  → 如在线获取公钥，必须与预置值严格匹配
  → 本地验证 Ed25519 签名
  → 校验 device_hash、有效期和模块
  → 加密保存信封
```

### 2.3 日常启动

1. 先读取本地信封并完成本地验签，网络不可用不应直接锁死软件。
2. 在线信封仅可离线使用到签名字段 `offline_valid_until`；在后台异步调用在线校验会刷新该时间。
3. 在线校验返回明确的吊销/过期错误时更新授权状态。
4. 调用版本检查；有更新时按产品策略提示或强制升级。

### 2.4 本地保存与模块门控

- License key 与签名信封分开保存；License key 使用操作系统凭据库或等效受保护存储，不写入普通日志、崩溃报告或明文配置。
- 只有验签及设备、时间、模块校验全部通过的信封才能替换本地有效信封。
- 软件根据 `payload.modules` 开放顶层产品模块：`eye_tracking` 对应眼动模块，`facial_analysis` 对应表情模块。
- 未授权模块可以隐藏或禁用，但进入模块路由、创建实验和启动采集等核心入口仍须再次校验，不能只依赖界面状态。
- 解绑成功后立即删除本地 License key 和授权信封；网络失败时不得误删仍处于离线宽限期内的有效信封。

### 2.5 机器码规则

- `machine_code` 是客户端生成的稳定机器标识原文，只在 HTTPS 请求体中发送。
- 服务端会先去除首尾空白、合并连续空白、转大写，再计算 SHA-256。
- `device_hash` / `machine_hash` 是上述标准化结果的十六进制 SHA-256，共 64 字符。
- 检查更新只需传哈希，不应把机器码原文放在 URL 查询参数中。

## 3. 客户端接口

### 3.1 健康检查

`GET /api/v1/health`

响应 `200`：

```json
{
  "status": "ok",
  "service": "ust-license-admin",
  "time": "2026-08-22T08:00:00Z"
}
```

该接口只表示 Web 进程可响应，不代表签名私钥、数据库外部依赖和对象存储全部正常。

### 3.2 在线激活

`POST /api/v1/client/activations`

请求：

```json
{
  "license_key": "UST-ABCD-EFGH-JKLM-NPQR",
  "machine_code": "设备生成的稳定机器码",
  "device_name": "实验室主机 01",
  "client_version": "1.0.0"
}
```

字段：

| 字段 | 必填 | 限制 | 说明 |
| --- | --- | --- | --- |
| `license_key` | 是 | 最长 40 | 后台签发的授权号 |
| `machine_code` | 是 | 4–500 | 只放请求体，不写日志 |
| `device_name` | 否 | 最长 120 | 方便后台识别设备 |
| `client_version` | 否 | 最长 40 | 当前桌面端版本 |

首次激活响应 `201`；同一 License + 机器码重复激活为幂等刷新，响应 `200`：

```json
{
  "activation_id": "0257c256-12fa-4e74-88f7-d8b19ab526f7",
  "created": true,
  "license": {
    "schema_version": 1,
    "algorithm": "Ed25519",
    "key_id": "ust-2026-01",
    "payload": {
      "license_id": "835dc02c-f8c9-402a-925a-99112d95e8a1",
      "customer": {
        "id": "1133544b-f1d7-43a3-8762-f6f9ab63fa25",
        "name": "某客户"
      },
      "device_id": "0257c256-12fa-4e74-88f7-d8b19ab526f7",
      "device_hash": "c699c699c699c699c699c699c699c699c699c699c699c699c699c699c699c699",
      "activation_mode": "online",
      "issued_at": "2026-08-22T08:00:00Z",
      "not_before": "2026-08-22T08:00:00Z",
      "expires_at": "2027-08-22T08:00:00Z",
      "offline_grace_days": 7,
      "offline_valid_until": "2026-08-29T08:00:00Z",
      "modules": [
        {
          "code": "eye_tracking",
          "name": "眼动采集",
          "expires_at": "2027-08-22T08:00:00Z"
        }
      ]
    },
    "signature": "base64url-ed25519-signature"
  }
}
```

签名只覆盖 `license.payload` 的规范 JSON；外层 `schema_version`、`algorithm`、`key_id` 和 `signature` 不进入签名输入，但客户端仍必须校验前三者是否为受支持值。当前 payload 限定为对象、数组、字符串、整数、布尔值和 null，不使用浮点数；所有对象递归按 ASCII 字段名升序排列，UTF-8 编码，分隔符 `,`/`:` 后无空格，非 ASCII 字符不转义。Electron 端应递归排序对象后再 `JSON.stringify`，数组顺序保持不变。

服务端不会把完整 `license_key` 放入签名信封，避免离线 `.lic` 文件泄漏在线激活凭证。客户端应将用户输入的 key 与签名信封分开存储，并按需加密保护。

### 3.3 在线校验/刷新

`POST /api/v1/client/licenses/verify`

请求字段与在线激活相同。此接口不会创建新设备；设备必须已激活且状态正常。

响应 `200`：

```json
{
  "valid": true,
  "activation_id": "0257c256-12fa-4e74-88f7-d8b19ab526f7",
  "license": {
    "schema_version": 1,
    "algorithm": "Ed25519",
    "key_id": "ust-2026-01",
    "payload": {},
    "signature": "base64url-ed25519-signature"
  }
}
```

`payload` 结构与激活接口完全一致。每次成功刷新都会更新设备的 `last_seen_at` 和客户端版本。

### 3.4 主动解绑

`POST /api/v1/client/activations/deactivate`

```json
{
  "license_key": "UST-ABCD-EFGH-JKLM-NPQR",
  "machine_code": "设备生成的稳定机器码"
}
```

响应 `200`：

```json
{
  "deactivated": true,
  "activation_id": "0257c256-12fa-4e74-88f7-d8b19ab526f7"
}
```

解绑后本地签名信封仍可能在离线时通过密码学验证，客户端必须立即删除本地授权缓存。服务端吊销状态为 `revoked` 的设备不能自助解绑或重新激活。

状态为 `deactivated` 的设备再次调用在线激活时复用原 `activation_id`，在设备额度仍充足时恢复为 `active` 并重新占用一个额度；如果额度已被其他设备占满，返回 `DEVICE_LIMIT_REACHED`。在线校验不会自动恢复已解绑设备。

`activation_mode` 描述签名信封，不是设备记录的永久状态。已有在线设备做离线签发、已有离线设备改在线激活时都复用同一个设备记录和额度；离线签发返回 `activation_mode=offline`，之后在线激活或在线校验返回新的 `activation_mode=online` 信封。客户端始终用最新验签成功的信封替换旧信封。

### 3.5 获取签名公钥

`GET /api/v1/client/signing-keys/{key_id}`

响应 `200`：

```json
{
  "key_id": "ust-2026-01",
  "algorithm": "Ed25519",
  "public_key": "base64url-32-byte-raw-public-key"
}
```

桌面端正式包必须至少内置当前生产公钥或其可信指纹。联网获取公钥适用于取值和轮换，但获取结果必须与客户端预置的 `key_id → 公钥/指纹` 严格匹配；没有对应预置信任条目时必须拒绝，不得直接用接口返回值验签。HTTPS 保护传输，但不能单独建立 License 的首次信任。

#### 3.5.1 密钥配置说明

执行：

```bash
python manage.py generate_signing_key
```

会输出一对匹配的 Ed25519 密钥：

```text
LICENSE_SIGNING_PRIVATE_KEY=<私钥>
PUBLIC_KEY=<公钥>
```

| 名称 | 实际用途 |
| --- | --- |
| `LICENSE_SIGNING_PRIVATE_KEY` | 后台环境变量；服务端签署 License 信封。只能保存在服务器或密钥管理系统中 |
| `PUBLIC_KEY` | 生成命令的输出标签；供复制到桌面端信任包，或者密钥轮换后写入 `LICENSE_PUBLIC_KEYS`。当前 Django 不读取同名环境变量 |
| `LICENSE_SIGNING_KEY_ID` | 当前活动密钥的稳定标识，例如 `ust-2026-01`；会出现在每个信封的 `key_id` 中 |
| `LICENSE_PUBLIC_KEYS` | 服务端保留的公钥 JSON 映射，主要用于继续提供历史 `key_id` 的旧公钥 |

当前活动公钥由服务端根据活动私钥派生，因此后台只配置当前私钥即可提供本接口。公钥可以随软件发布；私钥禁止进入客户端、数据库、Docker 镜像、Git、普通日志、聊天或工单。

`DEVICE_SECRET_ENCRYPTION_KEY` 不属于这对签名密钥。它只负责加密数据库里的 softdog pwd，必须独立生成、独立备份，不能与 License 私钥复用。

若私钥已经出现在非受控位置，应立即按泄露处理，而不是简单删除消息：停止旧私钥签名、生成新密钥对和新 `LICENSE_SIGNING_KEY_ID`、通过可信软件更新把新公钥加入客户端可信集合，同时撤销被攻破的旧 `key_id`，并重新签发合法 License。泄露事故不能继续无条件信任旧公钥到历史信封自然过期，否则攻击者仍可伪造旧 `key_id` 的信封；也不能回滚到已经泄露的旧私钥。当前第一版没有在线密钥撤销列表，必须通过客户端紧急更新实施撤销；仍联网的客户端可以同时强制在线校验，完全离线客户必须通过可信介质升级并换发 License。已签发旧离线信封的截止时间已经纳入签名，服务端事后缩短配置不会改变它。

正常且未发生私钥泄露时，密钥轮换按以下顺序执行：

1. 在密钥管理系统生成新密钥，旧私钥继续签名。
2. 发布仍由旧信任链认可的桌面端版本，在客户端预置新公钥/指纹，并同时保留旧公钥。
3. 确认目标客户端完成升级后，服务端切换 `LICENSE_SIGNING_KEY_ID` 和活动私钥。
4. 服务端把旧公钥保留在 `LICENSE_PUBLIC_KEYS`，客户端信任包也保留旧、新两把公钥，直到旧信封全部过期。
5. 若新密钥配置故障，可在确认旧私钥从未泄露的前提下从密钥管理系统恢复旧私钥和旧 `key_id`；匿名公钥接口本身不承担首次信任建立。

公钥接口返回的数据必须先匹配客户端通过可信安装包/更新预置的 `key_id → 公钥或指纹` 信任集合，才能用于 License 验签。仅有 HTTPS 连接和接口返回值不足以建立 License 的首次信任；新增生产公钥应通过已受信的软件更新或其他受控发布渠道分发。

### 3.6 检查更新

`GET /api/v1/client/releases/latest`

查询参数：

| 参数 | 必填 | 默认值 | 可选值/说明 |
| --- | --- | --- | --- |
| `product_type` | 否 | `pc` | `pc`（当前工程的 PC 端）或 `android`（独立移动端软件） |
| `platform` | 是 | — | PC 端使用 `windows`、`macos`、`linux`；安卓端使用 `android` |
| `architecture` | 否 | `x64` | `x64`、`arm64`、`universal` |
| `channel` | 否 | `stable` | `stable`、`beta` |
| `current_version` | 否 | 空 | 当前语义版本；非法版本按必须更新处理 |
| `machine_hash` | 否 | 空 | 64 位十六进制 SHA-256，用于稳定灰度 |

示例：

```http
GET /api/v1/client/releases/latest?product_type=pc&platform=windows&architecture=x64&channel=stable&current_version=1.0.0&machine_hash=c699c699c699c699c699c699c699c699c699c699c699c699c699c699c699c699
```

有可见版本时响应 `200`：

```json
{
  "update_available": true,
  "force_update": false,
  "release": {
    "version": "1.1.0",
    "product_type": "pc",
    "platform": "windows",
    "architecture": "x64",
    "channel": "stable",
    "changelog": "修复采集稳定性问题",
    "published_at": "2026-08-22T08:00:00Z",
    "file_sha256": "f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2f2e2",
    "file_size": 152043221,
    "download_url": "https://license.example.com/api/v1/client/releases/uuid/download"
  }
}
```

无可见版本或未命中灰度时：

```json
{
  "update_available": false,
  "release": null
}
```

`force_update=true` 的条件：目标发布强制更新、`current_version` 非法，或当前版本低于目标发布的 `minimum_supported_version`。这些场景绕过灰度，必须返回目标版本；省略 `current_version` 时服务端无法判断最低支持版本，只能根据发布自身的 `force_update` 决定。客户端应先保护正在进行的实验数据，再进入强制升级流程。

服务端在可见候选中按语义版本选择最高版本，并按以下互斥分支响应：

- `current_version` 是合法版本：只有低于目标时 `update_available=true`；等于或高于目标时两个标记均为 false，绝不重装或降级。
- `current_version` 缺失：只要存在目标版本即 `update_available=true`；`force_update` 仅沿用目标发布自身的强制标记，无法应用最低支持版本规则。
- `current_version` 非法：`update_available=true`、`force_update=true`，并绕过灰度，引导客户端恢复到可比较的正式版本。

### 3.7 下载安装包

`GET /api/v1/client/releases/{download_token}/download`

可选查询参数：

- `machine_hash`：设备哈希，用于下载统计。
- `client_version`：下载前客户端版本。

成功返回二进制文件和 `Content-Disposition: attachment`。下载完成后必须计算整个文件的 SHA-256，并与版本检查响应中的 `file_sha256` 做常量时间比较；不一致时删除文件并禁止安装。

SHA-256 只能确认文件与后台声明一致，不能独立证明软件发布者身份。生产安装包还必须使用平台代码签名（Windows Authenticode、macOS Developer ID/公证或等价机制）；客户端或安装器必须验证签名有效且发布者身份符合预期后才能执行。用于新增或撤销 License 公钥的软件更新必须通过这条独立可信发布链分发。

### 3.8 获取和下载测试工具

`GET /api/v1/client/test-tools`

返回后台已开启“允许下载”的测试工具。可选传 `platform=windows|macos|linux|android|universal`；传具体平台时，响应同时包含该平台和 `universal` 通用工具。每项包含名称、版本、平台、说明、文件大小、SHA-256 和不可枚举的 `download_url`。

```json
[
  {
    "id": "测试工具 UUID",
    "name": "眼动设备连接测试工具",
    "version": "1.0.0",
    "platform": "windows",
    "description": "用于检查设备连接与 softdog 配置",
    "file_sha256": "64位十六进制摘要",
    "file_size": 12582912,
    "download_url": "https://license.example.com/api/v1/client/test-tools/uuid/download",
    "updated_at": "2026-08-23T08:00:00Z"
  }
]
```

软件或网页直接请求 `download_url` 即可下载。后台关闭“允许下载”后，列表不再返回该工具，已有链接也立即返回 404。下载会记录时间、IP、User-Agent 和请求 ID。下载后应校验完整文件的 SHA-256；测试工具若会执行代码，也必须进行对应平台的代码签名。

| HTTP | `error.code` | 建议处理 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` / `INVALID` | 提示输入有误；开发阶段记录 details |
| 403 | `CUSTOMER_INACTIVE` | 锁定授权功能并联系运营 |
| 403 | `LICENSE_INACTIVE` | 提示授权未启用或已暂停 |
| 403 | `LICENSE_REVOKED` | 清除缓存并锁定授权功能 |
| 403 | `LICENSE_NOT_STARTED` | 显示生效时间 |
| 403 | `LICENSE_EXPIRED` | 提示续期 |
| 403 | `ONLINE_ACTIVATION_DISABLED` | 引导导入离线 License |
| 403 | `OFFLINE_ACTIVATION_DISABLED` | 改用在线激活 |
| 403 | `DEVICE_REVOKED` | 禁止自动重试，联系运营 |
| 403 | `DEVICE_INACTIVE` | 引导重新激活 |
| 403 | `NO_ACTIVE_MODULES` | 不开放任何授权模块，联系运营 |
| 404 | `LICENSE_NOT_FOUND` | 检查授权号 |
| 404 | `DEVICE_NOT_ACTIVATED` | 走首次激活流程 |
| 404 | `SIGNING_KEY_NOT_FOUND` | 使用内置公钥或升级客户端 |

网络超时、DNS、TLS 或 5xx 不等于 License 已失效。在线和离线签发使用相同规则：`offline_grace_days=0` 时，`offline_valid_until=expires_at`，仅受总授权期限限制；正数时为 `min(expires_at, issued_at + offline_grace_days)`。截止时间由服务端签名，客户端不得自行延长。软件仅显示总授权到期时间。任何模式都不得越过 `expires_at`。

### 5.1 管理客户眼动设备

设备类型与客户设备实例分开管理。`bootstrap_roles` 默认创建 A8、Pro、aSeeGlassesPlus 三种类型，也可以通过 `POST /eye-tracker-types/` 增加其他类型：

```json
{"code":"new-model","name":"新型号","manufacturer":"设备厂商","is_active":true}
```

为客户添加设备：

`POST /api/v1/management/customer-eye-trackers/`

```json
{
  "customer": "客户 UUID",
  "device_type": "眼动设备类型 UUID",
  "display_name": "实验室 A8 主设备",
  "serial_number": "A8-2026-0001",
  "status": "active",
  "softdog_password": "<64 位以上的设备密钥>",
  "notes": ""
}
```

`softdog_password` 对应设备配置中的：

```ini
[softdog]
pwd=<与设备对应的 softdog 密钥>
```

约束与安全规则：

- 一个客户可以关联多种类型、多台眼动设备；每台设备有自己的 softdog pwd。
- pwd 必须为 32–512 位十六进制字符串，服务端统一转为大写。
- pwd 使用 `DEVICE_SECRET_ENCRYPTION_KEY` 加密保存，API 字段只写不读。
- 响应只返回 `softdog_password_configured=true` 和 12 位 `softdog_password_hint`，不会返回明文或完整密文。
- 修改设备资料时可以省略 `softdog_password`，原密钥保持不变；需要换密钥时通过 PATCH 重新提交该字段。
- `serial_number` 非空时全局唯一；没有序列号可以留空。
- 客户详情响应包含只读 `eye_tracker_count` 和脱敏后的 `eye_trackers` 摘要。
- 设备列表可用 `?customer={uuid}`、`?device_type={uuid}`、`?status=active` 过滤。
- 当前阶段只完成后台保管和管理接口，不向桌面客户端公开下发 softdog pwd。后续需先确认按 License、客户或指定设备授权的下发规则。

### 5.2 创建并启用 License

1. `POST /customers/` 至少提交 `code`、`name`；默认状态为 `active`。
2. 产品模块当前只使用 `eye_tracking`（眼动模块）和 `facial_analysis`（表情模块）。`POST /modules/` 仅用于未来新增同级产品能力，至少提交稳定且不可复用的 `code`、`name`；禁止把 A8/Pro 等硬件型号或 AOI、刺激呈现、导出等子功能建成产品模块。
3. `POST /licenses/` 提交 `customer` UUID、`starts_at`、`expires_at`，可选 `max_devices`、在线/离线开关和 `offline_grace_days`。建议先使用默认 `draft`。
4. 对每个模块调用 `POST /license-items/`，提交 `license` UUID 与 `module` UUID；`expires_at` 为空时继承 License 到期时间。
5. 确认至少有一个启用且未过期模块后，`PATCH /licenses/{id}/` 提交 `{"status":"active"}`。

License 创建响应会返回只读 `license_key`。删除或替换模块前应评估已签发信封；后续在线校验会收到新模块清单，但旧离线信封直到自身有效期结束前不会自动变化。

### 5.3 上传与发布版本

创建版本使用 `multipart/form-data` 调用 `POST /releases/`，至少提交：

- `version`：语义版本，例如 `1.2.0`。
- `product_type`：`pc` 或 `android`；省略时兼容为 `pc`。
- `platform`：PC 端使用 `windows`、`macos` 或 `linux`；安卓端必须使用 `android`。
- `architecture`：`x64`、`arm64` 或 `universal`。
- `channel`：`stable` 或 `beta`。
- `package`：平台允许的安装包；服务端计算 `file_sha256` 与 `file_size`。
- `changelog`：建议填写；初始 `status` 使用 `draft`。

Windows 支持 `.exe/.msi/.zip`，macOS 支持 `.dmg/.pkg/.zip`，Linux 支持 `.AppImage/.deb/.rpm/.tar.gz/.zip`，Android 支持 `.apk/.aab`。同一产品端类型、平台、架构、渠道和版本不能重复创建。

上传完成并核对摘要后，调用 `PATCH /releases/{id}/`：

```json
{"status":"published","published_at":"2026-08-22T08:00:00Z","rollout_percentage":100}
```

省略 `published_at` 时服务端使用当前时间；设置未来时间表示定时发布。撤回使用 `{"status":"withdrawn"}`，撤回后检查和下载接口均不再提供该版本。重新发布同一记录前需重新评估缓存与客户端行为，不应新建相同目标的重复记录。

### 5.3.1 上传测试工具并取得下载链接

使用 `multipart/form-data` 调用 `POST /api/v1/management/test-tools/`，提交 `name`、语义版本 `version`、`platform`、`package`，可选提交 `description` 和 `is_active`。支持 `.exe/.msi/.zip/.dmg/.pkg/.AppImage/.deb/.rpm/.tar.gz/.apk`。

创建响应中的 `download_url` 就是可交给软件或客户使用的下载链接；后台 `/admin/releases/testtool/` 也会显示该资源并统计下载次数。`is_active` 使用列表开关控制，设为 `false` 时无需删除文件即可停止下载。工具文件更新必须新建版本，不建议在同一记录上静默替换已分发文件。

### 5.4 状态枚举与转换

| 对象 | 状态 | 说明/常用转换 |
| --- | --- | --- |
| Customer | `active`、`suspended`、`closed` | active 可激活；suspended/closed 均返回 `CUSTOMER_INACTIVE` |
| CustomerEyeTracker | `active`、`maintenance`、`retired` | active 正常；maintenance 维护中；retired 停用但保留历史和密钥密文 |
| License | `draft`、`active`、`suspended`、`revoked`、`expired` | draft→active；active↔suspended；active/suspended→revoked；过期时间仍由服务实时检查 |
| LicenseDevice | `active`、`deactivated`、`revoked` | deactivated 可在有额度时重新激活；revoked 只能由运营人员处理 |
| Release | `draft`、`published`、`withdrawn` | draft→published→withdrawn；下载只接受 published |

敏感对象不提供物理删除。状态字符串是接口契约，界面显示名称可以本地化，但客户端不得自行创造 `inactive` 状态值。

### 5.5 离线签发

`POST /api/v1/management/licenses/{license_id}/offline-license/`

```json
{
  "machine_code": "离线客户提供的机器码",
  "device_name": "实验室离线主机"
}
```

接口响应结构与在线激活相同，外层包含 `activation_id`、`created` 和 `license`。`.lic` 文件只保存响应中的 `license` 对象，禁止保存整个接口响应。

`.lic` 固定为 UTF-8 JSON，推荐扩展名 `.lic`，顶层必须且只能包含：

```json
{
  "schema_version": 1,
  "algorithm": "Ed25519",
  "key_id": "ust-2026-01",
  "payload": {},
  "signature": "base64url-ed25519-signature"
}
```

实际 `payload` 与第 3.2 节一致，`activation_mode` 为 `offline`。保存、传输或导入时不得修改 `payload`；客户端按 JSON 内容和 schema 校验，不依赖操作系统 MIME 类型。

离线签发会创建或复用 `LicenseDevice` 并占用 `max_devices` 额度。同一 License + 机器码重复签发复用原设备记录，不重复占额度；已解绑设备仅在仍有空余额度时恢复，已吊销设备禁止重新签发。离线信封的 `activation_mode` 为 `offline`，`offline_valid_until` 等于 `expires_at`。

管理接口完整字段以 OpenAPI 为准。日常运营可直接使用 `/admin/`，独立 Web 管理前端后续可基于这些接口开发。

## 6. License 本地验证清单

客户端接受 License 前必须全部通过：

1. `schema_version === 1`，`algorithm === "Ed25519"`。
2. 能找到 `key_id` 对应的受信公钥。
3. 对规范化 `payload` 验签成功。
4. 当前时间不早于 `not_before`，且同时不晚于签名的 `offline_valid_until` 和 `expires_at`。
5. 本机标准化机器码的 SHA-256 与 `device_hash` 完全一致。
6. 目标功能的模块编码存在，且模块自身 `expires_at` 未过期。
7. `license_id`、`device_id`、时间和数组类型均满足 schema，不接受隐式类型转换。

签名有效只代表内容由受信私钥产生，不代表客户端可以跳过时间、设备和模块校验。

完全离线环境无法从服务端获取可信时间，用户回拨系统时钟可能延长授权，这是第一版的固有限制。客户端应在操作系统受保护存储中保存历史最大可信时间（成功在线响应时间或已接受信封的 `issued_at`），当前时间明显早于该值时拒绝继续并提示校时。高风险部署应要求周期性在线校验或使用硬件可信时钟。

## 7. 联调前检查

- 后台已设置 `LICENSE_SIGNING_KEY_ID` 和私钥，客户端已取得匹配公钥。
- 生产后台已设置并安全备份 `DEVICE_SECRET_ENCRYPTION_KEY`。
- 每个客户眼动设备均已选择正确类型并设置独立 softdog pwd。
- 客户、License 均为有效状态，当前时间落在授权周期内。
- License 至少包含一个启用且未过期的模块。
- 设备上限留有额度。
- 软件版本已上传安装包、状态为 published、发布时间已到。
- 客户端和服务端机器码规范化算法一致。
- 客户端已验证激活幂等、超额度、吊销、过期、断网、本地验签失败和安装包摘要失败流程。
