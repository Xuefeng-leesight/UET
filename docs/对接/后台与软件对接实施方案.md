# UST 后台与软件对接实施方案

> 文档版本：1.1.0
> 更新日期：2026-08-23
> 适用范围：UST PC 端（当前 Electron 工程）、UST 安卓端（独立移动端软件）、UST License 与版本管理后台
> 后台接口版本：`/api/v1`
> 关联文档：`docs/接口/后台接口文档.md`、`docs/接口/openapi.yaml`、`docs/方案/License管理与版本更新后台方案.md`

## 1. 文档目标

本文用于指导后台、PC 客户端和安卓客户端完成以下闭环：

1. 软件首次启动时完成在线激活或导入离线 License。
2. 软件在每次启动和运行期间本地验证 License，不把“能否使用”完全依赖于网络。
3. 联网时刷新 License 状态，并在离线宽限期内支持断网运行。
4. 根据 License 中的产品模块控制眼动模块、表情模块及后续扩展模块。
5. PC 端和安卓端分别检查、下载和安装自己的软件版本。
6. 软件或下载页获取后台上传的测试工具及下载链接。
7. 后台运营人员可以完成客户、设备、License、软件版本和测试工具的日常管理。
8. 对接过程具备明确的错误处理、安全边界、验收步骤和上线回滚方案。

本文是实施方案，不是单纯的接口字段说明。开发人员应按照第 14 节的阶段顺序执行，每个阶段达到验收条件后再进入下一阶段。

## 2. 当前状态与实施边界

### 2.1 后台已经具备

- 客户、产品能力模块、眼动设备类型和客户眼动设备管理。
- 每个客户关联多种、多台眼动设备；每台设备独立保存加密后的 softdog pwd。
- License 创建、启用、暂停、吊销、到期和设备额度管理。
- 在线激活、在线刷新、主动解绑和离线 License 签发。
- Ed25519 License 签名、公钥查询和统一错误结构。
- PC/安卓产品端类型分离的软件版本发布、灰度、强制更新、下载和摘要校验信息。
- 测试工具上传、允许下载开关、不可枚举下载链接和下载记录。
- Docker、PostgreSQL、Nginx、Let's Encrypt HTTPS 和证书自动续期配置。

### 2.2 本轮执行状态

截至 2026-08-23，当前仓库中的 PC 端主体已经落地：

- Electron 主进程 License 领域、后台 API 客户端、Ed25519 验签、机器码、安全原子存储、可信时间和服务端锁定标记。
- 在线激活、在线刷新、离线 `.lic` 导入、主动解绑、授权摘要和启动激活页。
- 眼动/表情导航、新建项目、录制命令、表情服务和映射服务的模块门控；授权撤销时停止对应 Python 服务。
- `product_type=pc` 版本检查、强制更新阻断页、流式下载、大小/SHA-256/Windows Authenticode/发布者校验和安装器启动。
- 测试工具列表、受控后台下载链接和后台下载记录。
- 客户端构建配置示例见仓库根目录 `.env.example`。

当前仓库不包含安卓端源码，因此安卓实现仍需在移动端仓库按第 8 节落地。第 7.3 节的 Python WebSocket 短时令牌和完整 draining 协议属于下一轮安全加固；当前版本已通过“不授权不启动服务 + Electron 主进程业务命令门控”建立第一道边界，但在该协议完成前不应作为最终生产安全验收版本。

本次软件对接不包含以下内容：

- 客户端读取后台保存的眼动设备 softdog pwd。后台当前只负责安全保管，不提供公开下发接口。
- 账号登录、支付、订阅和客户自助门户。
- 增量更新或热更新。
- 安卓应用商店审核、上架和商店内更新流程；后台 `.apk/.aab` 发布属于自有分发能力。
- 通过 `/admin/` 页面给终端用户激活。`/admin/` 只供运营人员使用。

## 3. 已确定的对接原则

| 项目 | 实施决定 |
| --- | --- |
| PC 端标识 | `product_type=pc`，当前工程首先使用 `platform=windows`、`architecture=x64` |
| 安卓端标识 | `product_type=android`，`platform=android`；架构按实际包使用 `arm64` 或 `universal` |
| 激活输入 | 用户只输入 License key；机器码、设备名和客户端版本由软件自动获取 |
| 日常授权判断 | 先本地验签和有效期判断；联网刷新是状态同步，不替代本地验签 |
| License key 存储 | PC 使用 `safeStorage` 加密后写入应用私有目录，安卓使用 Keystore 保护；禁止明文写入普通 JSON、日志或项目数据目录 |
| License 信封存储 | 验签成功后加密保存，并采用原子写入 |
| 公钥信任 | 正式安装包内置受信 `key_id → public_key`；不能仅信任匿名接口返回的公钥 |
| 模块门控 | 页面入口、业务命令和底层能力三层校验，不能只隐藏菜单 |
| 更新策略 | 只升级不降级；下载后校验 SHA-256 和平台代码签名，再启动安装 |
| 网络策略 | 有限超时、有限重试、指数退避；网络失败不等于 License 失效 |
| 测试工具 | 与正式软件版本分开；链接由后台控制，关闭后旧链接失效 |

## 4. 总体架构与职责

```text
运营人员
  │  HTTPS + 后台登录
  ▼
UST 管理后台
  ├─ 客户、眼动设备、产品模块
  ├─ License、激活设备、离线签发
  ├─ PC/安卓版本发布
  └─ 测试工具上传与下载统计
  │
  │ HTTPS REST API
  ├───────────────────────────┐
  ▼                           ▼
UST PC 端                     UST 安卓端
Electron 主进程               原生网络/安全存储层
  ├─ 后台 API 客户端            ├─ 后台 API 客户端
  ├─ 机器码                    ├─ 安装实例标识/设备标识
  ├─ 安全存储                  ├─ Keystore 加密存储
  ├─ Ed25519 验签              ├─ Ed25519 验签
  ├─ 模块门控                  ├─ 模块门控
  └─ 下载与安装更新            └─ 下载/系统安装或商店更新
```

职责边界：

- 后台决定客户、License、设备额度、模块、有效期和发布版本。
- 客户端负责生成稳定机器码、保护本地凭证、验签、模块门控、更新下载校验和用户交互。
- 后台私钥永远不进入客户端。
- 客户端不直接连接后台数据库，也不解析后台管理网页。
- 渲染层不得直接持有 License key、原始机器码或文件系统写权限；这些能力放在 PC 主进程或安卓安全基础设施层。

## 5. 环境与配置

### 5.1 环境划分

至少建立三套相互隔离的环境：

| 环境 | 用途 | 数据与密钥要求 |
| --- | --- | --- |
| local | 单机开发 | 可使用本地数据库和专用开发密钥 |
| staging | 联调、验收、升级演练 | 使用独立域名、独立数据库、独立签名密钥 |
| production | 正式客户 | 生产域名、生产数据库和受控生产密钥 |

不同环境的 License、私钥、公钥和数据库不能混用。开发或 staging 私钥不得复制到生产环境。

### 5.2 客户端配置项

PC 和安卓端都应有构建期配置：

```text
UST_API_ORIGIN=https://license.example.com
UST_RELEASE_CHANNEL=stable
UST_PRODUCT_TYPE=pc 或 android
UST_PLATFORM=windows 或 android
UST_ARCHITECTURE=x64、arm64 或 universal
UST_TRUSTED_SIGNING_KEYS={"ust-2026-01":"base64url-public-key"}
```

要求：

- 正式包不允许用户在普通设置页任意修改 API Origin，避免被引向伪造服务。
- local/staging 可通过构建变量切换地址，但界面必须明确显示非生产环境。
- API Origin 只包含协议和主机，不以 `/` 结尾；请求层统一追加 `/api/v1`。
- 客户端版本取正式构建版本，不手工维护第二份版本号。PC 使用 Electron `app.getVersion()`，安卓使用 `versionName`。

### 5.3 对接接口总表

| 调用方 | 方法与路径 | 认证 | 用途 |
| --- | --- | --- | --- |
| PC/安卓 | `GET /api/v1/health` | 无 | 后台存活检查 |
| PC/安卓 | `POST /api/v1/client/activations` | License key 在请求体 | 首次在线激活或幂等恢复 |
| PC/安卓 | `POST /api/v1/client/licenses/verify` | License key 在请求体 | 已激活设备在线刷新 |
| PC/安卓 | `POST /api/v1/client/activations/deactivate` | License key 在请求体 | 解除本机激活 |
| PC/安卓 | `GET /api/v1/client/signing-keys/{key_id}` | 无 | 获取公钥值；只能与内置信任比对 |
| PC/安卓 | `GET /api/v1/client/releases/latest` | 无 | 按产品端/平台检查更新 |
| PC/安卓 | `GET /api/v1/client/releases/{token}/download` | token | 下载正式安装包 |
| PC/安卓/下载页 | `GET /api/v1/client/test-tools` | 无 | 获取允许下载的测试工具 |
| PC/安卓/下载页 | `GET /api/v1/client/test-tools/{token}/download` | token | 下载测试工具 |
| 运营后台 | `POST /api/v1/management/licenses/{id}/offline-license/` | staff Session/Basic | 签发离线 `.lic` 内容 |
| 管理系统 | `/api/v1/management/*` | staff Session/Basic | 客户、License、版本和工具管理 |

客户端禁止调用 `/api/v1/management/*`。完整字段和响应以 OpenAPI 为准；本方案定义调用顺序和本地行为。

## 6. 共享客户端数据契约

PC 和安卓端应实现等价的数据结构。字段名称保持后台原始 snake_case，减少映射错误。

### 6.1 License 信封

```ts
type LicenseEnvelope = {
  schema_version: 1;
  algorithm: 'Ed25519';
  key_id: string;
  payload: {
    license_id: string;
    customer: { id: string; name: string };
    device_id: string;
    device_hash: string;
    activation_mode: 'online' | 'offline';
    issued_at: string;
    not_before: string;
    expires_at: string;
    offline_grace_days: number;
    offline_valid_until: string;
    modules: Array<{
      code: string;
      name: string;
      expires_at: string;
    }>;
  };
  signature: string;
};
```

### 6.2 本地授权状态

```ts
type LocalLicenseState =
  | { state: 'unactivated' }
  | { state: 'valid'; envelope: LicenseEnvelope; source: 'cache' | 'online' | 'offline-file' }
  | { state: 'offline-grace'; envelope: LicenseEnvelope; remainingMs: number }
  | { state: 'not-started'; envelope: LicenseEnvelope }
  | { state: 'expired'; envelope?: LicenseEnvelope }
  | { state: 'device-mismatch'; envelope?: LicenseEnvelope }
  | { state: 'invalid-signature'; envelope?: LicenseEnvelope }
  | { state: 'clock-rollback'; envelope?: LicenseEnvelope }
  | { state: 'revoked'; reasonCode: string }
  | { state: 'service-error'; envelope?: LicenseEnvelope; retryable: boolean };
```

### 6.3 模块编码

| 模块编码 | 软件能力 |
| --- | --- |
| `eye_tracking` | 眼动采集、校准、眼动记录与依赖眼动数据的分析能力 |
| `facial_analysis` | 表情采集、表情分析与表情结果查看能力 |
| 后续编码 | 只能新增同级产品能力；发布后不可改变含义或复用旧编码 |

未知模块编码必须忽略并记录诊断信息，不能导致旧客户端崩溃。

- `electron/platform/python/pythonRuntime.ts`：取消启动阶段无条件启动眼动服务，改为授权后按需启动、授权失效后安全停止。
- `src/App.tsx`：通过 `LicenseGate` 先加载授权状态，再决定显示激活页或主应用。
- `src/app/layout/Sidebar.tsx` 和业务入口：按模块状态控制可见性与可操作性。
- `src/features/recording/domain/recordingWsModule.ts`：WebSocket 建连时加入主进程签发的短时本地会话令牌。
- `src/features/recording/domain/recordingStartModule.ts`：发送 `start_recording` 前检查项目模态与 License 模块。
- `src/modalities/registry.ts`：集中维护项目模态与 License 模块的唯一映射。
- `src/features/projects/NewProjectModal.tsx`：未授权模态不可选择，界面说明所需 License 模块。
- facial、mapping、analysis、recording 等 handlers：在真正启动服务或执行受限任务前调用统一门控。

不得把所有逻辑继续堆入 `electron/main.ts` 或 `MrtApplicationController.tsx`。

### 7.1 必须先改造的启动顺序

当前 `electron/main.ts` 在创建主窗口前执行 `ensureSoftdogKeyConfigured()` 和 `startPyServer()`。这与 License 门控冲突，必须改成：

1. 初始化日志、协议和最小窗口基础设施。
2. 加载机器码和本地 License 状态。
3. 创建主窗口；未激活时只显示激活页。
4. License 有效后初始化公共功能。
5. 只有授权 `eye_tracking` 且用户首次进入眼动能力时，才提示配置 softdog pwd 并启动眼动 Python 服务。
6. 只有授权 `facial_analysis` 且用户进入表情能力时，才启动表情服务。
7. License 失效时进入第 10.4 节的 draining 流程，安全收尾后关闭对应服务。

仅表情授权的客户不能被 softdog 配置阻塞，未激活用户也不能提前启动眼动服务。

### 7.3 现有 WebSocket 的门控改造

当前录制页面通过 `recordingWsModule.ts` 直接连接本地 Python WebSocket 并发送 `start_recording`。只在 Electron IPC 中门控是不够的。第一版确定采用“主进程签发短时本地会话令牌”的方案：

1. Python 服务只监听 loopback，不接受局域网直接访问。
2. 每次启动 Python 子进程时，主进程生成 32 字节 `boot_secret` 和随机 `boot_id`，只通过子进程环境变量传入；两者不写磁盘、不进入 renderer 和日志。
3. 主进程签发 HMAC-SHA256 令牌。payload 固定包含 `{v, boot_id, session_id, role, audience, modules, iat, exp}`；`role` 为 `session` 或 `controller`，`audience` 区分 eye/facial 服务，`modules` 只能来自当前已验证 License，`exp` 是建立连接的截止时间，默认 10 分钟。
4. renderer 通过受控 IPC 获取普通 session token；主进程另外持有不暴露给 renderer 的 controller token。
5. 命令、图像、眼动数据、编码视频和表情预览 WebSocket 都必须先认证；Python 在认证成功前不处理命令也不发送业务数据。
6. 令牌只通过 WebSocket 第一条消息传递，不放 URL，不写日志。认证消息和响应固定为：

```json
{"type":"authenticate","token":"base64url(payload).base64url(hmac)"}
```

```json
{"type":"authenticated","session_id":"随机会话ID","modules":["eye_tracking"],"expires_at":"ISO8601"}
```

失败响应为 `{"type":"auth_error","code":"TOKEN_INVALID|TOKEN_EXPIRED|MODULE_DENIED"}`，随后服务端关闭连接。

7. `exp` 只限制新建/重连。已经认证且正在录制的连接不会因为 10 分钟到期被强行中断；断线重连必须向主进程申请新令牌，主进程重新检查 License。
8. Python 对 `start_recording`、校准、眼动采集等命令再次检查 session 的 `eye_tracking`；表情任务检查 `facial_analysis`。
9. License 状态改变、用户解绑或强制更新时，主进程使用 `role=controller` 的 token 发送 `enter_draining`。Python 只允许 controller 调用 `enter_draining`、`shutdown` 和 session 撤销命令；`role=session` 调用这些命令一律返回 `CONTROLLER_REQUIRED`。进入 draining 后 Python 全局拒绝新认证和新业务任务，并撤销普通 session 的启动权限。
10. draining 期间只允许 `stop_recording`、`finish_recording`、`flush_data`、`get_status`、`close_session` 以及当前录制所需的已有数据流；其他命令返回 `LICENSE_DRAINING`。
11. 收尾完成或超时后主进程停止 Python 子进程。服务重启会生成新的 boot_secret/boot_id，旧令牌和旧连接全部失效。

HMAC payload 使用与 License 相同的规范 JSON规则，但它只是本机进程间授权，不替代后台 Ed25519 License 签名。Python 端需要新增认证状态、命令白名单和 controller 操作；主进程需要新增令牌签发器和 draining 控制器。

长期如要更强隔离，可把命令 WebSocket 代理到主进程；第一版不允许继续使用完全无认证的本地命令端口。

## 8. 安卓端落地结构

安卓端技术栈尚未在当前仓库中确定。无论使用 Kotlin/Java、Flutter 或 React Native，都应保持以下分层：

```text
licensing/
├── api             # 后台 REST 请求
├── crypto          # Ed25519 验签和规范 JSON
├── machine         # 安装实例/设备标识
├── storage         # Keystore 加密存储
├── repository      # 在线与本地数据协调
├── domain          # 授权状态机和模块门控
└── ui              # 激活、状态、离线导入

updater/
├── api
├── downloader
├── verifier
└── installer
```

默认参考基线为原生 Kotlin + Jetpack Compose、OkHttp/Retrofit、Android Keystore、WorkManager。若现有移动端不是该技术栈，不要求重写软件，但必须在开发任务中列出对应的网络、安全存储、后台任务和安装组件。拿到安卓仓库后第一项工作是记录：技术栈、包名、min/target SDK、versionName/versionCode 来源、正式签名证书 SHA-256 和自有 APK/应用商店更新渠道；这些参数未确定前只做共享契约与 golden vector，不开始平台存储和安装实现。

安卓端要求：

- 使用 Android Keystore 保护 License key 和本地信封加密密钥。
- 不建议直接使用可被系统恢复或频繁变化的硬件标识。第一版可生成随机安装 ID，首次生成后存入 Keystore 保护的本地存储，并与应用签名、包名等稳定上下文共同生成机器码。
- 卸载重装会丢失安装 ID并占用新设备额度，这是可接受的第一版限制；如业务不接受，应单独定义账号或后台人工迁移流程，不能依赖受限制的硬件序列号。
- 若自行分发 APK，下载完成后校验 SHA-256、包名和签名证书，再调用系统安装界面；应用不能静默安装。
- 若正式版本通过应用商店发布，后台版本接口只用于提示，实际安装跳转商店；后台不得同时强制安装自有 APK。

## 9. License 对接流程

### 9.1 软件启动状态机

启动顺序必须固定：

1. 生成或加载机器码。
2. 从安全存储读取 License key 和已保存信封。
3. 对信封执行完整本地验证。
4. 没有信封或验证不可恢复时显示激活页，不初始化受限业务模块。
5. 本地有效时先进入主界面；网络可用时在后台执行刷新。
6. 刷新返回新信封时，先验签再替换旧信封。
7. 本地超过 `offline_valid_until` 时阻止受限模块，要求联网刷新或导入有效离线文件。
8. 无论模式如何，达到 `expires_at` 后必须停止授权模块。
9. 更新检查在 License 状态确定后执行，但紧急强制更新可在激活页提供。

```text
无本地信封 ───────────────> 激活页
    │
有本地信封
    ▼
验签失败/设备不匹配 ──────> 锁定 + 诊断提示
    │通过
    ▼
检查 not_before/expires_at/offline_valid_until/历史可信时间
    ├─ 有效 ──────────────> 主界面 + 异步在线刷新
    ├─ 宽限到期 ──────────> 要求联网刷新
    └─ License 到期 ──────> 锁定模块 + 联系运营
```

本地数据组合必须按下表处理：

| License key | 信封 | 网络 | 启动行为 |
| --- | --- | --- | --- |
| 无 | 无 | 任意 | 显示激活页 |
| 有 | 无 | 在线 | 显示激活页并预填脱敏 key；用户确认后重新在线激活 |
| 有 | 无 | 离线 | 显示激活页，不能仅凭 key 离线运行 |
| 无 | 有效离线信封 | 任意 | 允许按信封运行；不自动调用 `/licenses/verify`，设置页提供“转为在线激活”并要求输入 key |
| 有 | 有效在线或离线信封 | 在线 | 先本地进入，再调用 `/licenses/verify`；若离线信封对应设备未变，也可得到新的在线信封 |
| 有 | 有效信封 | 离线 | 在 `offline_valid_until` 前运行，不发送请求 |
| 任意 | 无效/过期信封 | 在线 | 锁定模块；有 key 时允许用户确认后重新激活，无 key 时要求输入 key 或导入新 `.lic` |
| 任意 | 无效/过期信封 | 离线 | 锁定模块，要求导入有效 `.lic` 或联网 |

保存在线激活结果时采用一个加密容器同时保存 License key 和已验签信封，再执行原子替换，避免“信封保存成功但 key 保存失败”。离线导入只保存信封并明确标记 `activation_mode=offline`，因为 `.lic` 本身不包含 License key。

### 9.2 在线激活

接口：`POST /api/v1/client/activations`

请求：

```json
{
  "license_key": "UST-ABCD-EFGH-JKLM-NPQR",
  "machine_code": "客户端生成的稳定机器码",
  "device_name": "实验室主机 01",
  "client_version": "1.0.0"
}
```

客户端执行步骤：

1. 用户输入后去除首尾空格并转大写；只在内存中保留明文。
2. 禁用重复提交按钮，显示正在激活。
3. 请求连接超时建议 5 秒，总超时建议 15 秒。
4. 收到 `200/201` 后验证响应字段完整性。
5. 使用内置受信公钥验证签名。
6. 比较 `payload.device_hash` 与本机 `SHA-256(normalize_machine_code(machine_code))`；规范化规则必须与后台一致：去首尾空白、转大写、连续空白压缩为一个空格。
7. 检查时间和至少一个有效模块。
8. 把 License key、新信封和状态元数据组成一个容器，整体加密后执行一次原子替换；不存在“先保存信封、再保存 key”的两步提交。
9. 原子提交成功后再更新内存状态并进入软件首页；提交失败则保持旧容器不变并提示激活未完成。

任何一步失败都不能把未验证信封写入正式缓存。

### 9.3 本地验签算法

签名输入只包含 `envelope.payload`，算法要求：

1. 对象字段按 ASCII 字段名升序递归排列。
2. 数组保持原顺序。
3. 使用 UTF-8。
4. JSON 分隔符后无空格。
5. 非 ASCII 字符按 UTF-8 原文处理，不转成 `\uXXXX`。
6. 对规范 JSON 字节执行 Ed25519 验签。
7. `schema_version` 必须为 `1`，`algorithm` 必须为 `Ed25519`。
8. `key_id` 必须存在于安装包内置可信集合；匿名公钥接口只能用于取值或轮换比对。

验签通过后仍要继续校验：设备哈希、`not_before`、`expires_at`、`offline_valid_until`、模块有效期和历史可信时间。

### 9.4 在线刷新

接口：`POST /api/v1/client/licenses/verify`

推荐触发点：

- 软件启动且网络可用时。
- 从休眠恢复且距上次成功刷新超过 12 小时。
- 用户在 License 管理页点击“刷新授权”。
- 即将超过 `offline_valid_until` 时。

第一版正常刷新间隔固定为 12 小时，失败后使用 1 分钟、5 分钟、30 分钟、2 小时退避；一次运行最多自动重试四次。`4xx` 业务错误不自动高频重试。

刷新失败策略：

- 网络超时、DNS、TLS 或 5xx：保留本地有效信封，并显示非阻断联网状态。
- `LICENSE_REVOKED`、`LICENSE_INACTIVE`、`DEVICE_INACTIVE`：进入 draining 并持久化锁定原因。当前后台刷新接口把所有非 active 设备统一返回为 `DEVICE_INACTIVE`，客户端不要假设刷新时一定能区分“已解绑”和“已吊销”。
- `DEVICE_NOT_ACTIVATED`：引导重新激活，不能自动占用新额度。
- 新信封验签失败：继续使用仍有效的旧信封并上报安全告警，不覆盖缓存。

收到任何已认证 HTTPS 业务拒绝后，客户端保存加密的 negative marker：`license_id`、`device_id`、错误码、响应 `Date` 头对应的服务端时间、当时信封的 `issued_at`。其中 `LICENSE_REVOKED`、`LICENSE_INACTIVE`、`CUSTOMER_INACTIVE`、`LICENSE_EXPIRED`、`DEVICE_INACTIVE` 进入持久化锁定。锁定后：

- 重新导入 `issued_at` 不晚于 negative marker 服务端时间的旧 `.lic` 必须拒绝，防止用吊销前文件回退。
- 只有成功的在线激活/刷新、不同的有效 License，或 `issued_at` 晚于 marker 服务端时间的新离线信封可以解除锁定。
- 新离线信封仍须完成签名、机器码和时间校验；后台在 License/设备仍不可用时本身不会签发它，因此“较新”代表运营端已明确恢复并重新签发。
- 响应缺少或无法解析 `Date` 时使用 `max_trusted_time`，并把该情况写入脱敏诊断。

### 9.5 离线激活

第一版操作流程：

1. 软件激活页显示可复制的机器码和设备名称。
2. 客户把机器码交给运营人员。
3. 运营人员调用 `POST /api/v1/management/licenses/{license_id}/offline-license/`，提交 `machine_code` 和可选 `device_name`，生成响应。
4. 只把响应中的 `license` 对象保存为 UTF-8 `.lic` 文件。
5. 客户在软件中选择“导入离线授权”。
6. 软件限制文件大小，例如不超过 1 MB，并按 JSON 解析。
7. 执行与在线信封完全相同的 schema、受信公钥、签名、设备和时间校验。
8. 验证通过后加密保存并替换旧信封。

禁止导入整个管理 API 响应；`.lic` 顶层只能是 `{schema_version, algorithm, key_id, payload, signature}`。

纯离线导入后本地没有 License key，因此不执行自动在线刷新。用户以后要切换到在线模式时，在 License 管理页选择“转为在线激活”，重新输入 License key 后调用在线激活接口；成功后再把 key 和新的在线信封作为一个加密容器原子保存。

### 9.6 主动解绑

接口：`POST /api/v1/client/activations/deactivate`

用户确认解绑后：

1. 调用接口。
2. 成功后立即删除本地 License key、信封和授权状态缓存。
3. 清理运行中的受限模块并回到激活页。
4. 不删除客户项目和实验数据。

断网时不允许仅在本地假装解绑，否则后台设备额度不会释放。可提供“清除本地授权”作为单独的高风险操作，但必须明确提示仍需联系运营人员释放后台额度。

## 10. 模块授权门控

### 10.1 门控函数

客户端统一实现：

```ts
hasModule(code: string, at = new Date()): boolean
requireModule(code: string): void
```

判断条件：

- 当前 License 状态允许运行。
- `modules` 中存在相同 `code`。
- 模块自身 `expires_at` 晚于当前可信时间。

### 10.2 三层门控

| 层级 | PC 示例 | 作用 |
| --- | --- | --- |
| 导航层 | Sidebar 隐藏或禁用表情/眼动入口 | 提供清晰用户体验 |
| 页面/命令层 | 进入 Recording、FacialAnalysis 前调用 `requireModule` | 防止通过旧路由或状态绕过 |
| 主进程/服务层 | 启动 Python 服务、SDK、采集、分析 IPC 前再次校验 | 形成真正安全边界 |

眼动和表情同时授权时，两套能力都可使用；只授权其中一个时，项目管理等公共能力可保留，但未授权模块不得启动相关服务或新建相关任务。

### 10.3 License 模块与现有项目模态映射

映射只在 `src/modalities/registry.ts` 附近的共享配置维护一份：

| License 模块 | 项目模态 | 受控能力 |
| --- | --- | --- |
| `eye_tracking` | `eye-tracking` | 眼动设备配置、校准、眼动采集、visual、mapping、aoi、chart、insight |
| `facial_analysis` | `facial-expression` | 摄像头表情采集、facial 页面、表情分析任务和结果 |

公共页面规则：

- 工程管理、受试管理和实验设计：只要至少一个产品模块有效即可使用。
- 新建项目：只显示已授权模态；至少选择一个已授权模态。
- 实验录制：页面可打开，但眼动和表情采集开关分别按模块授权；开始录制前检查当前实际启用的采集模态。
- 实验记录和原始数据导出：允许查看和导出客户已有数据，避免授权变化造成数据被扣留；不得由此启动新的分析计算。
- eye-tracking 的 visual/mapping/aoi/chart/insight：必须有 `eye_tracking`。
- facial 页面和新表情分析：必须有 `facial_analysis`。
- 导入旧项目包含未授权模态时：项目以“受限只读”标记打开；已有原始数据可查看/导出，未授权模态不能新采集、重算或进入专属分析页。
- License 缩减时不修改项目文件中的模态定义，防止数据结构被静默破坏。

### 10.4 运行中失效状态

授权失效和强制更新统一使用三态：

```text
active → draining → locked 或 update-required
```

- `active`：允许开始和执行任务。
- `draining`：持久化锁定原因，立即禁止新录制、新分析和新导出任务；若正在录制，主动发起优雅停止并允许现有媒体、CSV、元数据和索引完成落盘。
- `locked`：收尾完成后撤销本地服务令牌并停止对应服务，只保留 License 管理和已有数据的安全查看/导出入口。
- `update-required`：收尾完成后进入强制更新页，不再启动受限服务。

draining 默认最长 10 分钟，可通过受控构建配置调整。超时后记录诊断并强制停止子进程，但不得删除已落盘文件。锁定原因写入加密本地状态；重启后按第 9.4 节 negative marker 规则恢复，旧离线文件不能解除已确认的服务端锁定。多人实验由本机协调端发出停止命令并等待远端确认；远端失联时按现有故障收尾流程记录不完整状态。

License 在软件运行中失效时：

1. 持久化失效原因并进入 draining。
2. 禁止开始新的受限任务，主动安全结束正在执行的任务。
3. 完成安全收尾后回到授权提示页并关闭受限服务。
4. 不删除既有项目数据。

## 11. 软件版本对接

### 11.1 检查更新

接口：`GET /api/v1/client/releases/latest`

PC 示例：

```http
GET /api/v1/client/releases/latest?product_type=pc&platform=windows&architecture=x64&channel=stable&current_version=1.0.0&machine_hash=<64位机器哈希>
```

安卓示例：

```http
GET /api/v1/client/releases/latest?product_type=android&platform=android&architecture=arm64&channel=stable&current_version=1.0.0&machine_hash=<64位机器哈希>
```

检查时机：

- 启动完成后异步检查一次。
- 用户在“关于/版本更新”页面主动检查。
- 长时间运行的软件每 24 小时最多自动检查一次。

### 11.2 更新决策

| 后台结果 | 客户端行为 |
| --- | --- |
| `release=null` | 不提示 |
| `update_available=false` | 显示已是最新版本；绝不降级 |
| `update_available=true, force_update=false` | 弹出可稍后处理的更新提示 |
| `update_available=true, force_update=true` | 先保护实验数据，再阻止开始新任务并要求升级 |

强制更新不得直接杀死正在录制或正在写入的数据。收到结果后持久化 `update-required`：

1. 没有运行任务时立即进入更新页。
2. 正在录制时进入 draining，禁止新任务并主动优雅停止；默认收尾时限 10 分钟。
3. 录制期间不下载大文件，避免占用磁盘和网络影响数据；收尾完成后再下载。
4. 正在导出或分析时允许当前原子输出步骤结束，但不开始下一批任务，同样受 10 分钟总时限约束。
5. 安装包下载并校验完成后保存“待安装”状态；应用异常退出或重启时，在启动受限服务前恢复更新页。
6. 用户不得选择“跳过本次强制更新”；下载失败时只能重试或退出。
7. 多人实验由协调端触发 draining 并通知参与端停止；协调端完成状态汇总后才退出安装。

### 11.3 PC 下载与安装

1. 下载放在 Electron 主进程，渲染层只接收进度。
2. 请求后台返回的 `download_url` 时追加 `machine_hash=<本机64位哈希>&client_version=<当前版本>`，用于后台下载统计。
3. 使用临时目录和随机文件名，不直接覆盖正式安装目录。
4. 支持取消；网络中断后第一版可重新下载，不要求断点续传。
5. 完成后计算完整文件 SHA-256，并与后台 `file_sha256` 做常量时间比较。
6. 验证 Windows Authenticode 签名和预期发布者。
7. 校验失败立即删除文件并记录脱敏诊断信息。
8. 通知渲染层保存工作，等待主窗口和 Python 子进程安全关闭。
9. 启动安装器后退出应用。
10. 新版本首次启动再次读取原有安全存储并执行 License 验证。

后台当前允许 `.exe/.msi/.zip`，正式自动更新优先发布签名后的 `.exe` 或 `.msi`，不要让客户端直接执行来源不明的 `.zip` 内容。

### 11.4 安卓下载与安装

- 自有分发：下载 APK，校验 SHA-256、包名、版本号和签名证书，然后调用系统安装界面。
- 应用商店：后台只提示版本和更新内容，实际跳转商店详情页。
- AAB 只用于应用商店上传，普通安卓设备不能直接安装 AAB。
- 客户端构建时必须确定一种正式更新渠道，不能在同一渠道中随机切换自有 APK 和商店签名包。

软件设置页或单独下载页展示：名称、版本、平台、说明、文件大小和更新时间。后台返回的 `download_url` 是实际下载地址。

## 13. 网络、错误和安全规范

### 13.1 HTTP 客户端统一规则

- 只允许 HTTPS 生产地址。
- 默认请求头：`Accept: application/json`、唯一 `X-Request-ID`、明确客户端版本和平台 User-Agent。
- JSON 请求使用 `Content-Type: application/json; charset=utf-8`。
- 连接超时 5 秒、普通请求总超时 15 秒；大文件下载单独配置空闲超时。
- 只对网络错误、`429` 和部分 `5xx` 重试；尊重 `Retry-After`。
- 日志记录方法、路径模板、状态码、请求 ID、耗时和错误码，不记录 License key、机器码、签名信封、Authorization 或 softdog pwd。

### 13.2 主要错误处理矩阵

| 错误码 | 软件行为 |
| --- | --- |
| `LICENSE_NOT_FOUND` | 提示检查 License key，不自动重试 |
| `CUSTOMER_INACTIVE` | 锁定授权模块并联系运营 |
| `LICENSE_INACTIVE` | 提示授权未启用或已暂停 |
| `LICENSE_REVOKED` | 锁定模块，保留诊断摘要 |
| `LICENSE_NOT_STARTED` | 显示生效时间 |
| `LICENSE_EXPIRED` | 锁定模块并提示续期 |
| `ONLINE_ACTIVATION_DISABLED` | 引导离线授权 |
| `OFFLINE_ACTIVATION_DISABLED` | 运营人员改用在线激活 |
| `DEVICE_LIMIT_REACHED` | 展示设备额度信息，提示解绑旧设备 |
| `DEVICE_NOT_ACTIVATED` | 进入首次激活流程 |
| `DEVICE_INACTIVE` | 引导重新激活或联系运营 |
| `DEVICE_REVOKED` | 禁止自动恢复，联系运营 |
| `NO_ACTIVE_MODULES` | 不开放产品模块，联系运营 |
| `SIGNING_KEY_NOT_FOUND` | 使用内置可信公钥；必要时升级客户端 |
| `PACKAGE_NOT_FOUND` | 重新检查版本，仍失败则联系运营 |
| `TOOL_PACKAGE_NOT_FOUND` | 刷新工具列表 |
| `THROTTLED` | 按 `Retry-After` 延迟 |
| `SERVICE_NOT_CONFIGURED` | 服务端配置故障，停止频繁重试并告警 |

接口差异：在线激活和主动解绑可以明确返回 `DEVICE_REVOKED`；当前 `/licenses/verify` 对 deactivated/revoked 都返回 `DEVICE_INACTIVE`。客户端在刷新路径显示“本机激活状态不可用”，具体原因由运营人员在后台确认，不能根据一次刷新响应擅自恢复设备。

### 13.3 本地存储

PC 端建议：

- 使用 Electron `safeStorage` 加密 License key 和信封。
- 加密前检查 `safeStorage.isEncryptionAvailable()`；不可用时拒绝把明文凭证落盘，并显示可诊断错误。Windows 正式包不得降级到明文存储。
- 密文保存在 `app.getPath('userData')/licensing/`。
- 文件权限限制为当前用户。
- 使用临时文件、刷盘和原子替换，避免断电产生半个 JSON。
- 保存 `max_trusted_time`。本地时间比它倒退不超过 5 分钟时按时钟误差处理；超过 5 分钟进入 `clock-rollback`，但仍允许请求在线刷新。成功验签的新在线信封以签名后的 `issued_at` 修复可信时间基线。

安卓端使用 Keystore 包装本地加密密钥，密文保存在应用私有目录。两端都不得把授权数据放入项目目录、导出包或云同步目录。

### 13.4 机器码建议

PC Windows 第一版先生成本地机器描述，不允许各开发人员自行选择字段：

```text
UST-MACHINE-V1|WINDOWS|MG=<Windows MachineGuid>|BIOS=<Win32_ComputerSystemProduct.UUID>
```

取值后去首尾空白并转大写；字段内部连续空白压缩为一个空格。某字段无法取得时写 `-`，但两项都缺失时生成 32 字节随机安装种子，使用 safeStorage 加密保存，并把本地描述改为：

读取值必须过滤全零 UUID、全 `F`、`UNKNOWN`、`DEFAULT`、`TO BE FILLED BY O.E.M.` 等厂商占位值；过滤后按缺失处理。

```text
UST-MACHINE-V1|WINDOWS|SEED=<base64url安装种子>
```

客户端对本地描述的 UTF-8 字节做 SHA-256，最终提交的 `machine_code` 固定为：

```text
UST-MACHINE-V1|SHA256=<64位小写十六进制>
```

后台再对这个最终机器码按“去首尾空白、转大写、连续空白压缩为一个空格”规范化后做 SHA-256。客户端比较信封 `device_hash` 时必须执行同样的第二次哈希。原始 MachineGuid、BIOS UUID 和安装种子不得离开客户端，也不得写日志。

安卓端本地描述固定为 `UST-MACHINE-V1|ANDROID|PKG=<包名>|CERT=<签名证书SHA-256>|INSTALL=<Keystore保护的随机安装ID>`，同样先做本地 SHA-256，再提交上述 `UST-MACHINE-V1|SHA256=...` 格式。卸载重装导致安装 ID 变化时按新设备处理。

要求：

- 系统重启、应用升级、用户名变化后保持稳定。
- 普通网卡变化不应导致机器码改变。
- 克隆系统镜像前必须清除 MachineGuid/BIOS 克隆风险并走系统封装流程；使用 fallback 种子的镜像必须在封装前删除种子，让每台机器首次启动重新生成。
- 机器码算法一旦发布不能随意改变；需要升级时增加 `machine_code_version` 的内部前缀，并设计兼容迁移。
- x64 应用运行在 Windows ARM64 时，更新架构按安装包/进程支持策略上报，首版 x64 包仍上报 `x64`，不能仅根据操作系统误报 `arm64`。
- `max_trusted_time` 文件损坏或丢失时进入需要联网刷新或重新导入离线 License 的恢复状态，不静默重建为当前系统时间。

### 13.5 公钥正常轮换

正常轮换严格按以下顺序，后台不能先切换签名私钥：

1. 生成新 `key_id` 和密钥对，私钥只进入后台受控环境。
2. 发布仍由旧信任链认可的新客户端，新客户端同时内置旧、新公钥。
3. 观察版本覆盖率；达到业务确认的最低覆盖率后，后台切换到新 `key_id` 和私钥。
4. 过渡期后台继续通过 `LICENSE_PUBLIC_KEYS` 提供旧公钥，客户端继续信任旧、新信封。
5. 等旧信封全部过期且旧客户端完成升级后，后续客户端版本才移除旧公钥。

每次轮换都要提供共享签名 golden vector：固定 payload、规范 JSON 的 UTF-8 十六进制或 base64、key_id、公钥、签名和预期验证结果。Python、TypeScript 和安卓实现必须对同一个向量得到一致结果。

## 14. 分阶段实施计划

### 阶段 A：共享协议与基础设施

PC 任务：

- 新增 License/Release/TestTool 类型定义。
- 新增统一后台 HTTP 客户端和错误解析。
- 新增机器码、安全存储、规范 JSON 和 Ed25519 验签。
- 新增 IPC 白名单、handlers 和 renderer client。
- 重构 `electron/main.ts` 启动顺序，在 License 状态确定前不启动 softdog 流程和眼动/表情服务。

安卓任务：

- 建立等价的数据结构、HTTP 客户端、Keystore 存储和验签组件。
- 固定包名、签名证书、产品端类型、平台和架构参数。

验收：

- staging `/api/v1/health` 可访问。
- Python、PC 和安卓能用第 13.5/16.1 节共享 golden vector 得到完全相同的规范 JSON 字节，并完成签名通过、篡改失败、设备不匹配失败。
- 日志中不存在 License key 和机器码。

### 阶段 B：在线与离线激活

- 实现启动授权状态机和独立激活页。
- 完成在线激活、刷新、离线导入、状态摘要和主动解绑。
- 实现历史可信时间和离线宽限判断。

验收：

- 首次激活返回 `201`，同机重复激活返回 `200` 且不增加设备数。
- 超过设备额度得到明确提示。
- 断网时在宽限期内可启动，超过宽限期不可启动授权模块。
- `.lic` 内容被篡改、机器不匹配或过期时拒绝导入。
- 解绑后后台设备变为 deactivated，本地回到激活页。

### 阶段 C：模块门控

- 实现统一 `hasModule/requireModule`。
- 接入导航、页面和主进程/服务三层门控。
- 在项目模态注册表建立唯一映射，处理新建项目和既有受限项目。
- 为本地 Python WebSocket 增加短时会话令牌、模块 claims 和撤销机制。
- 处理运行中授权失效的安全收尾。

验收：

- 仅眼动授权不能启动表情服务。
- 仅表情授权不能启动眼动 SDK 和采集。
- 双模块授权可正常使用两者。
- 修改后台授权后，客户端刷新可得到新模块清单。

### 阶段 D：PC 与安卓版本更新

- 实现版本查询、普通/强制更新交互。
- 实现流式下载、进度、取消、SHA-256 和代码签名校验。
- 实现 PC 安装器启动或安卓系统安装/商店跳转。

验收：

- PC 只获取 `product_type=pc` 的版本，安卓只获取 `product_type=android`。
- 同版本不更新，高版本客户端不降级。
- 摘要不一致的文件被删除且不能执行。
- 强制更新不会破坏正在录制或写入的数据。
- 新版本启动后 License 状态仍可恢复。

### 阶段 E：测试工具与运营闭环

- 软件设置页展示测试工具列表和下载进度。
- 后台运营人员完成工具上传、链接复制、开关和下载记录查看。
- 完成客户开通、License 签发、设备激活、版本发布全流程演练。

验收：

- 工具开启时可下载并通过摘要校验。
- 后台关闭后旧链接立即失效。
- 下载次数增加且包含请求 ID。

### 阶段 F：staging 验收与生产发布

- 执行第 16 节全部场景。
- 使用正式安装方式完成升级演练。
- 对生产域名、证书、密钥备份、数据库备份和回滚包做最终检查。
- 先发布内部和少量客户，再扩大范围。

## 15. 后台运营执行流程

### 15.1 给新客户开通

1. 在“客户管理 → 客户”创建客户，状态为 active。
2. 如需登记硬件，在“客户眼动设备”添加设备类型、序列号和该设备自己的 softdog pwd。
3. 在“License 管理 → License”创建 License，填写生效时间、到期时间、设备上限和在线/离线策略。
4. 添加眼动模块、表情模块或两者。
5. 确认模块和有效期后，把 License 状态切换为 active。
6. 把 `UST-...` License key 通过受控渠道交给客户。
7. 客户激活后，在“激活设备”确认设备名称、版本和最后在线时间。

客户眼动硬件与软件激活电脑是两个不同对象，运营人员不能把二者混为一条记录。

### 15.2 发布软件版本

1. 生成正式构建并完成平台代码签名。
2. 在“版本管理 → 软件版本”创建 draft。
3. PC 选择 `product_type=pc` 和对应桌面平台；安卓选择 `product_type=android, platform=android`。
4. 上传安装包，核对后台 SHA-256 与构建系统产物摘要一致。
5. 填写更新日志、最低支持版本、是否强制和灰度比例。
6. 小范围 staging 下载和安装通过后改为 published。
7. 观察下载记录和客户端反馈，再逐步扩大灰度。
8. 发现问题时切换为 withdrawn；不要删除历史记录。

### 15.3 发布测试工具

1. 在“版本管理 → 测试工具”上传包并填写平台、名称、版本和说明。
2. 核对 SHA-256。
3. 打开“允许下载”。
4. 从后台复制下载链接，或由软件调用工具列表接口展示。
5. 停止分发时关闭开关，不直接删除历史文件和记录。

## 16. 联调与验收矩阵

### 16.1 staging 固定基线

每轮联调前由后台负责人幂等准备以下数据，名称和版本不要随意改变：

| 数据 | 固定值/要求 |
| --- | --- |
| 客户 | `STG-INTEGRATION`，active |
| 双模块 License | 眼动+表情、active、1 台设备、7 天离线宽限 |
| 眼动 License | 仅眼动、active、1 台设备 |
| 表情 License | 仅表情、active、1 台设备 |
| 状态场景 License | 各准备 suspended、revoked、未来生效、已过期记录 |
| PC 版本 | `product_type=pc, platform=windows, architecture=x64`，普通和强制各一条 |
| 安卓版本 | `product_type=android, platform=android, architecture=arm64`，普通和强制各一条 |
| 测试工具 | Windows active 一条、Windows inactive 一条、universal active 一条 |

### 16.2 执行与证据

| 角色 | 职责 |
| --- | --- |
| 后台负责人 | 准备基线、切换 License/版本状态、提供请求 ID 对应的后台结果 |

每个场景记录：前置数据 ID、操作步骤、客户端版本/架构、请求 ID、实际响应码和错误码、客户端状态变化、后台记录变化、证据链接、执行人、日期和通过/失败。签名向量必须由 Python、TypeScript 和安卓各自验证，三端输出的规范 JSON 字节必须完全相同。

## 17. 上线、监控与回滚

### 17.1 上线顺序

1. 部署后台和数据库迁移。
2. 执行 `bootstrap_roles`，确保新增模型权限同步到运营角色。
3. 确认 HTTPS、健康检查和备份正常。
4. 先发布包含内置生产公钥的 PC/安卓客户端。
5. 创建内部 License 完成生产冒烟检查。
6. 发布测试客户，再逐步发放正式 License。
7. 最后启用强制更新策略。

### 17.2 监控指标

- 激活成功率和各错误码数量。
- `DEVICE_LIMIT_REACHED`、签名错误和时钟回拨出现次数。
- License 刷新失败率和请求耗时。
- 不同产品端类型、版本和平台的下载次数。
- 安装包或测试工具 404、摘要失败和安装失败数量。
- 后台 5xx、数据库健康、磁盘/对象存储容量和证书续期状态。

### 17.3 回滚

- 后台代码回滚前必须确认数据库迁移兼容；优先向前修复，不随意回滚已写入的新数据结构。
- 有问题的软件版本在后台设为 withdrawn，并重新发布更高的修复版本，不能用较低版本覆盖。
- 不对已安装客户端自动降级。
- License 签名私钥泄露时不能简单回滚旧私钥；必须轮换 key_id、发布撤销旧信任的客户端并重新签发。
- 测试工具有问题时关闭“允许下载”，保留记录以便审计。

- 客户、License、模块、版本和测试工具运营手册。
- Docker 部署、备份和恢复说明。

PC 端交付：

- License/Updater 主进程领域模块。
- IPC 契约和渲染层页面。
- 内置可信公钥配置。
- 签名安装器、构建摘要和版本发布说明。
- 联调验收记录。

安卓端交付：

- 等价 License 状态机和安全存储实现。
- 固定包名、签名证书指纹和更新渠道说明。
- 签名 APK/AAB、构建摘要和版本发布说明。
- 联调验收记录。

## 19. 开发开始前必须确认的事项

以下事项不阻塞后台，但应在各客户端进入正式实现前确认：

1. 安卓端具体技术栈、包名、签名证书和正式更新渠道。
2. PC 首发是否只支持 Windows x64；若是，macOS/Linux 暂不在界面展示。
3. 默认 License 设备数；客户端第一版刷新周期已按 12 小时实施，若业务要求更短需评估服务容量。
4. 用户能否在离线场景自行清除本地授权，以及后台设备额度的人工处理流程。
5. 眼动设备 softdog pwd 未来是否需要下发给软件；如需要，必须另行设计按客户、License 和具体硬件授权的受保护接口。
6. 是否接受 draining 默认 10 分钟；未确认前按本文默认值实施。
7. 测试工具下载是否长期匿名，还是后续改为客户鉴权下载。

未确认项应记录负责人和截止日期。不能用临时代码绕过签名、设备匹配、模块门控或 HTTPS。

## 20. 第一轮开发任务拆分建议

建议以四个可独立验收的工作包安排：

| 工作包 | 主要工作 | 完成标志 |
| --- | --- | --- |
| PC-LIC-01 | PC 类型、API、机器码、安全存储、验签、IPC 和启动顺序重构 | 未激活时不启动 softdog/眼动服务；可在 staging 激活并重启恢复 |
| PC-LIC-02 | 激活/状态 UI、离线导入、刷新、解绑、项目模态映射、WebSocket 令牌和模块门控 | L01–L11、M01–M03 通过，直接 WebSocket 不能绕过授权 |
| PC-UPD-01 | PC 更新检查、下载、摘要/签名校验和安装 | U01、U03–U07 通过 |
| AND-LIC-UPD-01 | 安卓 License、模块门控和更新 | 安卓对应验收全部通过 |

测试工具面板可在 PC-UPD-01 后追加，也可以先使用独立 HTTPS 下载页完成第一版分发。
