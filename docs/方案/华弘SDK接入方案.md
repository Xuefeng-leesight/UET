# 华弘 SDK 接入方案

日期：2026-09-19。2026-10-07 实施更新：两款设备的独立生产适配、型号选择、进程启动、校准、录制及回放/导出兼容入口已新增；Windows 真机与安装包验收待执行。当前实现与限制见 [华弘运行说明](../../services/eye_tracking/adapters/huahong/README.md)，SDK 使用/清理见 [SDK 标记](../../SDK/huahong/README.md)。下文保留前期方案，目录与启动方式以本次运行说明为准。

## 1. 结论与范围

新增的四个目录是两个 Windows SDK 和两个 Android SDK，不应在桌面软件中直接显示为四种硬件。文档中的厂商名称为“华弘智谷”（用户称“华宏”），正式 UI 名称可再统一。

本次范围为 Windows x64：桌面式设备使用 ET10C Windows SDK；连接 Windows 电脑的 ET28 眼镜使用 ET28 Windows SDK。先完成 ET10C，再完成 ET28，各自独立验收。两套 Android SDK 仅保留资料，不开发 Android 采集端，不新增网络桥接，也不纳入本次安装包增量。

交付目标有三个，必须同时满足：

1. **接入成功**：正式 Windows 安装包在目标实机上完成连接、预览、校准、追踪、录制、结束收尾、重启回放、分析和导出，不以“DLL 能加载”或“收到一个点”作为完成。
2. **已有功能不回归**：Pro、A8、aSeeGlassesPlus、已有项目、历史记录及非眼动功能保持原有行为；以修改前基线和修改后对照结果为依据。
3. **新增风险可阻断、可回退**：华弘功能按型号独立启用；异常不污染旧设备配置与数据；发布时不得存在本次引入的已知未修复缺陷。

不能在没有实机验证的情况下保证“绝对零 bug”。本方案将要求落实为隔离设计、基线回归、异常测试和发布门槛；任一必测项未通过或未执行，都不能声称整体接入成功或无回归。

保留现有 Electron + React + Python WebSocket 服务。采用增量驱动与华弘专用转换入口，**不借此重构原有 aSee 驱动、校准和数据处理链路**。优先 ctypes 调用 C 导出接口，只有 ABI 或性能验证不通过时才考虑小型 C++ 包装层。

## 4. 目标结构及契约

数据路径：React 设备与校准界面 → 现有 WebSocket 命令 → SDKService → 型号驱动 → 厂商 SDK。华弘回调经专用适配器转换为应用可消费的样本/帧，再进入预览、录制与导出；旧设备继续走原回调路径。

建议新增 `services/eye_tracking/drivers/huahong_et10c.py`、`huahong_et28.py`、对应 ctypes 类型文件，以及华弘使用的样本类型模块。保留 `sdk_driver.py` 的 factory 入口和旧驱动原有实现，不要求旧驱动迁移到新适配器。

驱动契约复用现有生命周期：加载、启动设备、停止设备、启动/取消/完成校准、启动/停止追踪、释放资源；增加能力查询和设备信息。新增华弘业务入口不得访问厂商指针或依赖 aSee 字段；已有 aSee 字段读取逻辑在本次保持原行为。

建议稳定型号 ID：`HH_ET10C`、`HH_ET28`，运行时目录与型号 ID 分离，避免升级 SDK 时修改项目数据。具体 ID 是本方案建议，实施时全链路统一；本次不增加 Android 连接配置。

能力描述至少包括：场景视频、眼图、校准点数/模式、物理参数要求、时间戳来源、原生眨眼、授权方式。尚未验证的能力不显示为可用；不要沿用 aSee 的三/五/九点或卡片校准菜单作为华弘已支持的结论。

现有 `start`、`stop`、`start_calibration`、`start_calibration_point`、`start_tracking`、`start_recording`、`stop_recording` 等命令继续复用。在运行时信息响应中附加型号、SDK 版本、能力、连接状态；错误统一分类并保留厂商原始错误码。

## 5. ET10C Windows 接入

### 生命周期与接口映射

1. `getSystemDevicesList` 枚举 → 用户选择设备 → `createDevice` 获取句柄；空句柄视为失败。
2. 收集物理参数，调用 `ET10C_init`，注册设备、眼图、校准单点完成及追踪回调，启动 `ET10C_startCamera`。回调注册顺序按随包 demo 和真机验证固化。
3. 校准使用 `ET10C_performOnePointCalibration`，必要时 `ET10C_reConfig`；完成后检查 `ET10C_checkCalibrationFinished` 并读取 `ET10C_getCalibBias`。
4. 用 `ET10C_getCalibFeatureLen` 和保存/加载校准接口保存当前被试的校准数据；成功加载后才启动追踪。
5. `ET10C_startTracker` / `ET10C_stopTracker` 控制追踪。退出依次取消校准、停止追踪、停止相机、`ET10C_Deinit`；句柄最终释放语义需厂商确认，当前枚举头文件未给出单独 destroyDevice。

### 参数与数据

`ET10C_init` 要求屏幕宽高毫米值、屏幕与摄像机角度/距离、底部边框高度等。需要在设备设置中明确填写、校验并保存，不能将 demo 默认值作为所有硬件的通用配置。绑定实验显示器，复用现有多屏录制匹配，避免校准与录屏落在不同屏幕。

头文件给出不同设备的分辨率/帧率示例，demo 也有多种帧率启动脚本；它们不是对所有设备的承诺。先确认枚举型号和固件，再提供允许的预设；录像帧率与眼动采样率独立显示。

追踪结果有左右眼有效标志、合并屏幕点、左右眼点、视线、瞳孔信息及 `currTimePts`。优先使用有效的合并点，其次使用有效单眼/双眼合成；合成方法写入元数据。坐标范围通过 demo 与实机角点试验确认，时间单位/起点需补充确认。

`ET10C_checkEyeBlinkLincense` 是独立眨眼授权，readme 要求用设备信息向厂商申请授权文件。基础眼动与眨眼能力分开；未授权不显示原生眨眼结果。软件已有派生眼动事件若适用，应明确标注算法来源。虹膜注册/识别 API 不纳入本次眼动采集接入。

## 6. ET28 Windows 接入

### 生命周期与校准

`et28_device_init` → 注册设备状态回调 → `et28_device_connect` → `et28_getCamera_para` / `et28_setCamera_para` → 注册图像与追踪回调 → `et28_startCamera`。校准和追踪按各自初始化/释放生命周期调用 `et28_InitCalibration`、`et28_initTracker` 等。

逐点校准调用 `et28_performOnePointCalibration`，根据校准模式完成 `et28_MergeLRCalibration`、`et28_getCalibBias` 和数据保存。合并顺序以 demo 各模式为准，不把左右眼分开校准和双眼同时校准混用。

第一版提供经验证的场景目标校准：在场景预览标定真实目标位置并让被试看向目标。demo 校准点使用比例坐标，追踪点则直接画到场景图像上；二者不能使用同一套未经转换的坐标。卡片式校准需要另行验证当前卡片识别流程与华弘目标坐标是否兼容，首版不自动继承。

### 图像和同步

- demo 将场景回调数据作为 `CV_8UC3`，眼图作为 `CV_8UC1`；场景是原始图像路径，不能套用 aSee H.265 包处理。颜色顺序、步长、长度仍需实机验证。
- `worldPointLeft/Right` 在 demo 中直接当场景像素点绘制；适配层保存原始像素，并根据当前实际场景宽高转换成统一比例坐标。双眼均有效时可参考 demo 均值策略，但记录为应用合成，不能称为厂商融合点。
- 当前 `TrackInfoCb` 与 `CameraCallback` 未暴露设备时间戳/帧号。回调入口立即记录同一主机单调时钟与序号，保留 `timestamp_source=host_arrival`；它只表达接收时间，不能承诺采样级严格同步。
- 帧和注视样本用有界队列缓冲；录像走原始场景编码路径，预览可降频，眼动数据不随 UI 降频丢弃。记录丢帧、队列积压和匹配偏差。超出时间窗的样本标记未匹配，不强行覆盖到最近画面。
- 同步验收需要场景目标运动等可观察事件测量实际偏差；若实验要求硬件精确同步，应先向厂商索取带时间戳/帧号接口，再决定是否可满足。

## 7. 统一数据、校准存储和稳定性

统一样本至少保存：左右眼有效性、原始/归一化注视点、坐标空间、实际分辨率、设备时间（若有）、主机接收时间、会话相对时间、时钟来源、型号/SDK 版本。瞳孔图像尺寸不能未经换算写成毫米直径；缺失值用空值和有效标志表达，不能伪造零值或 aSee 的事件统计。

旧型号的 CSV 表头、列顺序、单位、文件命名及录像路径保持基线。华弘优先输出现有可兼容字段，额外字段保存在仅华弘记录使用的版本化元数据中；确需新格式时增加按版本读取，不改写历史文件。明确新增字段单位。关联检查范围包括 `sdk_service.py` CSV 输出、Electron 录制解析、前端注视点模型、分析与导出，确保旧记录仍可读取，新记录可正确回放和分析。

校准文件作为厂商不透明数据保存，外层记录格式版本、厂商/型号、SDK 版本、设备标识（可取得时）、场景分辨率或屏幕物理参数及校验值。设备/参数不匹配时要求重新校准，不跨厂商复用现有 aSee 系数。文件放在可写应用数据/项目目录，不覆盖 SDK 自带 `cablic.dat` 或 `test.CalibrationData`。

ctypes 绑定必须核验调用约定、`bool`/enum/int64 的大小、结构体对齐、嵌套布局及回调寿命。Windows 编译小型 `sizeof/offsetof` 探针与 Python 定义对照；头文件有 extern C 但包含 C++ 默认成员值/class，并不等于可以忽略 ABI 验证。

原生回调只复制数据、标时并入队，不执行文件写入、视频编码或 WebSocket 发送。单点校准可能阻塞数秒，使用专门任务与取消状态通知通道；UI 取消通知不能排在同一个被阻塞的工作队列后面。真正的 SDK 中断调用须先确认厂商线程安全规则，详见 10.2。通过会话/尝试编号丢弃过期回调，确保取消、断连和超时不会误报校准成功。

华弘两包存在同名依赖（如 OpenCV、ncnn、libusb）。涉及华弘的型号切换必须启动干净的 Python 采集进程，隔离 DLL 搜索路径；旧型号之间原有切换策略不在本次调整。录制/收尾期间禁止进入华弘切换流程。重启前正常停止并确认收尾，等待旧进程退出和端口释放，再启动新进程、重新连接 WebSocket 并核对型号；失败进入明确的未连接状态，不能遗留假连接或自动继续录制。不要把所有 SDK 的 bin 目录加入全局 PATH。若以后需要多设备同时采集，再按设备独立进程扩展；ET28 当前 C API 无设备句柄，不能直接承诺同进程多台。

## 8. 不影响已有内容的实施边界

### 8.1 修改前建立基线

在当前用户认可的代码状态上记录 Git 提交、已有未提交改动、SDK 文件校验值、运行环境、依赖与现有检查结果；不假定当前 HEAD 就是可用版本，也不覆盖用户改动。保存一份旧版可用安装包和匿名化测试项目/记录副本，所有对照测试在副本执行。

对三个旧型号分别记录完整操作链、命令/事件关键字段、校准保存加载结果、CSV 表头与单位、录像时长、回放叠加、分析/导出结果和运行资源指标。确定性数据按字段或文件对比；时间戳、实时帧率等非确定值使用明确的容差。基线已有缺陷单独记录，避免误认为新增问题，也不在本任务中顺手改动。

### 8.2 增量接入与默认关闭

- 为 ET10C 和 ET28 分别设置内部启用开关。开发与验证期间默认关闭，通过型号级验收后才在发布配置中开放；关闭时隐藏新选项、拒绝新驱动启动，不影响旧设备。
- 开关关闭时，不探测、不加载华弘 DLL，不更改旧型号默认值、softdog 逻辑及 Python 启动路径。
- 历史项目的缺省型号、别名及设备类型归一化保留原行为。华弘使用明确 ID 独立分支，型号缺失、包损坏或功能关闭必须明确报错，禁止回落 Pro/aSee。
- 不批量迁移旧项目，不修改旧校准文件，不将新设备配置写入旧 SDK config.ini；设备设置按厂商/型号保存。已有项目更换型号必须使用现有明确保存动作，并使不匹配校准失效。
- 公共协议只增加兼容的可选字段，不改变旧事件名称、成功/失败含义、旧字段单位与缺省行为。共享消费者确需修改时，先有基线测试，再添加仅新型号/新格式使用的分支。
- 不升级 Electron、React、Python 及公共依赖，不重写录像/分析/导出模块，不修改固件和 SDK 原文件，不顺带整理旧 SDK 安装包。

### 8.3 改动分批与可审查性

建议分成独立提交：基线测试 → 华弘型号/开关及运行时解析 → ET10C 驱动与闭环 → ET28 驱动与闭环 → 安装包和回归证据。每批写清新增文件、共享改动与验证结果；共享改动若导致旧输出变化，先停在该批修复，不继续堆叠功能。

## 9. 实施顺序与交付门槛

工期以通过验收为准。原方案 13–21 个工作日仅为设备齐备时的粗估，不包含本次强化的完整基线、故障注入与回滚验证；P0/P1 完成后再给出可靠排期，不用压缩回归换取按时交付。

| 阶段 | 工作 | 必须通过的门槛 |
| --- | --- | --- |
| P0 原有功能基线 | 保存当前状态、旧安装包、旧项目/记录副本，运行现有检查，建立回归样例 | 清楚哪些已通过、哪些原来有问题、哪些缺设备未测；无基线不能改共享链路 |
| P1 独立实机验证 | 在主业务之外运行 Windows 官方 demo 和最小 ctypes 探针，确认 ABI、生命周期、版本、授权、时间及坐标 | ET10C/ET28 各自有真实输出、校准及释放证据；未通过的型号不进入可用设备列表 |
| P2 增量接入基础 | 型号开关、路径清单、严格华弘解析、隔离进程启动和私有数据转换 | 关闭华弘开关时旧路径基线通过；无 SDK/损坏 SDK 不影响旧型号 |

### 10.2 异常注入与数据保护

必须覆盖：DLL/依赖缺失、授权失败、设备占用、初始化中途失败、无有效眼动、校准超时/取消/重试、采集中拔插、回调在停止后到达、WebSocket 中断、Python 进程异常退出、磁盘满/不可写、视频编码失败，以及录制/收尾中请求切换型号。

要求：用户获得准确错误；不能假成功；已落盘数据保留，未完成记录标注中断状态；不把残缺文件标为可用完成记录，不保证恢复尚未落盘数据。停止/释放操作幂等，断连后新会话不接收旧回调；队列满时计数并告警，必要时安全停止，不能静默丢失科研样本。恢复后可重新连接，旧设备仍可正常启动。

单点校准取消的并发调用以厂商线程安全规则为前提；未确认可并发前，不用另一个线程盲目调用 SDK 停止接口。不可中断时进入取消等待状态，超时后在保护录制数据的前提下重启设备进程。

### 10.3 自动检查与证据

实施后执行 `npm run check:sdk` 和 `npm run release:check`，增加 Windows ABI 探针、华弘数据映射/有效性/时钟测试、校准状态机测试、型号选择和历史数据兼容测试。自动测试应覆盖真实边界，不仅断言实现自身常量。

每项验收记录：代码版本、安装包校验值、操作系统、设备型号/固件、SDK 版本、步骤、预期、实际、日志及样例记录、通过/失败/未执行。静态检查和模拟测试不能替代 Windows 实机验收。本次只是修订方案，未执行这些新增测试。

发布阻断：任一必测项失败或未执行、本次新增缺陷尚未修复、型号/坐标/单位/时间语义不明、旧输出出现未解释变化、数据丢失、崩溃/死锁、安装依赖缺失或回退失败。修复后重跑相关用例及共享路径回归，不以关闭错误提示作为修复。

### 10.4 回退方案

1. 型号级故障：关闭对应华弘开关，保留诊断和已采集数据，旧型号继续使用；该措施不能替代共享代码回归。
2. 共享层回归：退回已保存的旧版安装包/代码状态，验证旧项目和旧设备恢复。新记录原样保留；旧版本不能识别的新数据不强行导入或转换。
3. 安装前备份用户配置及测试/生产数据，避免数据库或文件不可逆迁移。本次不改变软件许可证状态，不清理旧校准及 SDK 配置。
4. 在测试机实际演练“旧版 → 新版 → 回退旧版”，验证项目、许可证、SDK 路径、校准与回放。完成演练后才允许发布。
